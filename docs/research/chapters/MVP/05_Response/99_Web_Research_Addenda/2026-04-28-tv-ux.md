**Distilled findings.** `androidx.tv.material3` reached **1.0.0
stable** in September 2024 and is at **1.1.0-rc01** in April 2026,
with `androidx.tv.foundation` releases tracking the same cadence
(last published 2026-04-08 per the official release page). The
graduation from alpha collapsed the original split between `tv-foundation`
and the platform `compose-foundation`: scrollable containers
(`LazyRow`, `LazyColumn`, `LazyVerticalGrid`) now live in
`androidx.compose.foundation` directly and are TV-aware via a
focus-pinned scrolling behaviour that keeps the focused item glued to
the leading edge. The TV-specific `androidx.tv.material3` package
keeps the Material-3-on-TV components: `Carousel` (with
`AutoScrollDuration`, indicator slot, focus-pause behaviour),
`ImmersiveList` (background changes when row item is focused — the
`clickable` modifier now works on `ImmersiveList` per the 2026
release-note diff), and `TabRow` (top-navigation tabs that load on
tab-title focus rather than on click — the TV idiom). Focus
plumbing comes from compose-ui core: `Modifier.focusable()`,
`Modifier.focusGroup()`, `Modifier.focusRequester()`, `FocusManager`
methods (`moveFocus(FocusDirection)`), `Modifier.focusRestorer()`
(restores focus to the last focused child of a group when re-entered),
and `Modifier.bringIntoViewRequester()` (`BringIntoViewRequester
.bringIntoView()` scrolls all parents to expose a child) — the four
APIs the chapter prescribes for the shelf / hero / details screen
pattern. **MC-05 (Compose for TV stable) verdict:** validated. Ship
Compose for TV as the canonical Android TV surface.

**Distilled findings.** SwiftUI's TV focus model is built on
`@FocusState` (a property wrapper whose value is any Hashable type
representing the currently focused element ID), `focusable(_:)` (mark
a view as a focus target), `focused(_:equals:)` / `focused(_:)`
modifiers (bind a view's focus state to a specific value of a
`@FocusState` property), `focusScope(_:)` (constrain focus
preferences to a namespace — preserves "default focus" semantics
inside that scope), `prefersDefaultFocus(_:in:)` (mark the default
focus target on first scope entry), and `isFocused` (environment
variable, read-only, true when the nearest focusable ancestor is
focused). New in **tvOS 17** and confirmed unchanged in tvOS 18 is
the `hoverEffect(.highlight)` style which adds the
parallax-perspective shift + specular shine ("white shine")
characteristic of the Apple TV remote swipe — the chapter prescribes
this as the HelixPlay default focus effect to inherit the platform
visual idiom (Insight #6 reinforcement: lean on platform conventions).
Top Shelf is delivered as a separate `TVTopShelfContentProvider`
target (File ▸ New ▸ Target ▸ TV Services Extension) with two styles
(static images for non-frequently-updated apps; **Dynamic** for OTT /
gaming surfaces — the HelixPlay path); image specs are 1920×720 for
1080p Apple TV and 3840×1440 for Apple TV 4K, 16:9 aspect, with
`TVTopShelfSectionedItem` / `TVTopShelfInsetItem` / full-screen
content provider variants. HDR pipeline: `AVPlayer` is the only
tvOS API path that triggers Dolby Vision and Dolby Atmos passthrough
(no separate developer license required); HelixPlay's tvOS client
uses `AVPlayer` for game preview trailers and stitches its custom
WebRTC / UDP video surface for live gameplay through a CAMetalLayer
sibling — Top Shelf and trailer paths share the AVFoundation track.

**Distilled findings.** `androidx.leanback` is officially **deprecated**
in the Jetpack release notes; the canonical Google migration page
(`developer.android.com/training/tv/playback/leanback/migrate-to-compose`)
prescribes a **hybrid co-existence** path: Compose-View bridges
inside Leanback fragments, fragment-by-fragment replacement starting
with settings / account screens, and final consolidation into a
single-Activity Compose app. Compose for TV's minimum API level is
**21 (Android 5.0)**, which actually exceeds Leanback's reach into
older sets, so the "legacy SoC fallback" argument is largely a
marketing-deck artefact rather than a technical one. The 2026 forcing
function is **64-bit app compatibility**: Google's August 2025 blog
mandates 64-bit-only TV apps starting **August 2026**, which retires a
substantial swathe of legacy 32-bit Leanback installs and effectively
makes the Compose-for-TV migration "now-or-soon" for any app that
wants to remain in the Play Store TV channel beyond 2026. **HelixPlay
posture:** Compose-for-TV is the single Android TV target; no hybrid
Leanback fragments ship in the MVP; the only place Leanback survives
is a documented deprecated-package import-ban in the lint config
(extends C05's policy). No 32-bit ABIs in any HelixPlay TV APK.

**Distilled findings.** On Android TV, voice search travels through
the **TV Search Provider** content-provider URI surface: Assistant
queries the provider, the cursor returns rows with
`SUGGEST_COLUMN_INTENT_ACTION` / `SUGGEST_COLUMN_INTENT_DATA`, and
when the Assistant fires the resulting Intent it adds
`EXTRA_START_PLAYBACK = true` for "play X" phrasings (vs.
`ACTION_VIEW` for "find X"). Richer fulfillment uses **App Actions
built-in intents (BIIs)** declared in `shortcuts.xml` — relevant ones
for HelixPlay: `actions.intent.GET_THING` (catalog lookup),
`actions.intent.OPEN_APP_FEATURE`, and `actions.intent.PLAY_GAME` (no
official media-class BII for cloud-gaming sessions in 2026, so
HelixPlay declares `OPEN_APP_FEATURE` with a `gameId` parameter). On
tvOS, the **App Intents** framework (introduced iOS 16, fully
available on tvOS 17+) supersedes the older SiriKit Media Intents
path; HelixPlay declares `AppIntent`-conforming structs for "play
game", "resume last session", "open library" and exposes them via an
`AppShortcutsProvider` so they appear in Siri, Spotlight, and the
Shortcuts app on Apple TV. Fire TV is the awkward outlier: **VSK
(Video Skills Kit) is no longer supported** as of the current Amazon
developer documentation (the page literally states "Video Skills Kit
(VSK) is no longer supported. For questions about existing
integrations, please contact your Amazon technical account manager").
The Amazon-supported path for new 2026 apps is the generic Alexa
microphone-button query routed through the launcher's universal
search; HelixPlay therefore registers content with Fire TV's catalog
ingestion and relies on the launcher for "watch X" phrasings rather
than implementing a custom voice surface. This is recorded in §Z as
contradiction Z-1 (cloudgaming_dim11 listed VSK as the recommended
Fire TV path).

**Distilled findings.** The EBU broadcast safe-area numbers (action
safe = 93 % of frame ≈ 3.5 % margins; title safe = 90 % ≈ 5 %
margins) survive into 2026 as a **convention even though most modern
TVs no longer overscan by default** — EDID since version 2 (CEA
861-A) carries an "underscan supported" capability bit and lets a
display advertise its native pixel mapping to the source, but
practical setups still encounter HDMI receivers, switchers, and
projectors that drop or rewrite that bit. Google's TV layout guide
codifies the 5 % margin as **48 dp horizontal × 27 dp vertical** for
Android TV (some sources cite 58 dp / 28 dp — both are within the
title-safe envelope; HelixPlay picks 48 dp / 27 dp as the canonical
overscan inset and reserves the additional 10 dp / 1 dp as visual
padding inside content). Leanback's `BrowseSupportFragment` already
applies these insets internally, so the chapter explicitly forbids
double-padding when migrating to Compose for TV. The Compose-for-TV
default is **no implicit safe-area inset**: the chapter prescribes a
`SafeArea` composable wrapping the root content, parameterised by
device class (Android TV / Fire TV / generic AOSP TV) and tested
against EDID-reporting and EDID-mute hardware. tvOS exposes
`safeAreaInsets` per scene, but Apple TV's HomeKit-curated experience
generally hides overscan — HelixPlay still applies `safeAreaPadding`
for parity.

| https://www.flatpanelshd.com/guide.php?subaction=showfull&id=1753780501 | Guide to HDMI CEC: Control your TV and media player with a single remote — FlatpanelsHD | 2026-04-29 | §11 |
| https://www.hdmi.org/spec/hdmi2_1 | HDMI 2.2 Specification Technology Overview — HDMI Forum | 2026-04-29 | §11 |

**Distilled findings.** **ALLM** is a single bit in the HDMI 2.1
auxiliary video information (AVI InfoFrame) — the source asserts
"this is gaming content, please switch to Game Mode" — and the
display flips into its lowest-latency profile (typically 5–25 ms
display-pipeline reduction depending on panel). Of the HDMI 2.1
features (VRR, ALLM, QFT, QMS, HFR), **ALLM is the most widely
implemented** in 2026 budget and premium panels; FlatpanelsHD's
support matrix shows ALLM in nearly every HDMI-2.1-marketed TV from
LG, Samsung, Sony, Hisense, TCL, and Panasonic from 2021 onward.
HelixPlay asserts the ALLM bit on the host-agent side whenever a
gameplay session enters the foreground; the TV client cannot itself
flip ALLM (it has no HDMI-source role), but it **can** consume the
display's reported low-latency state via Android TV's
`HdmiControlService` and surface a "Game Mode active" overlay.
**HDMI-CEC 2.0** (the version Android Open Source Project supports
on both source and sink devices) handles power events: One Touch
Play (controller wakes TV from standby), System Standby (controller
sleeps the TV when leaving HelixPlay), Active Source change, and
Remote Control Passthrough. The `HdmiControlManager` Android API
exposes these to apps with `MANAGE_CEC_CLIENT` permission (system
signature on most TVs), so HelixPlay declares the permission
opportunistically and degrades gracefully on non-rooted retail
panels by falling back to vendor-specific intents (Sony Bravia, TCL,
Sharp). HDMI 2.2 (announced 2025) preserves ALLM semantics and adds
Latency Indication Protocol metadata for sub-frame display latency
reporting — the chapter records this as a Phase-2 enhancement, not
MVP. ALLM-driven display path latency reduction stacks **additively**
with the encode/transport budget in C04 (frame pacing) and §12
(latency engineering overview), shaving an additional 10–25 ms off
the C12-ENERGY end-to-end budget.

**Distilled findings.** Trailer auto-play on focus is the de-facto
console-and-streaming idiom (PS5 store, Apple TV app, Netflix,
Disney+) but is a **WCAG 2.2 trip-wire**: SC 2.2.2 (Pause, Stop,
Hide) requires that any auto-updating content lasting more than five
seconds offer a mechanism to pause / stop / hide; SC 2.3.3 (Animation
from Interactions, AAA) covers vestibular-disorder triggers; and
`prefers-reduced-motion` must be honoured. Netflix's recent (March
2026) rollout of a hidden "disable auto-preview loop" setting was a
direct response to recurring user complaints — the ACM 2024 study
(76 Netflix users) measured a statistically significant reduction in
average daily watching when previews were disabled, evidence that
auto-play is sticky but is unwanted by a measurable fraction of
users. **HelixPlay rules** (chapter prescription): (1) auto-play
trailer fires after a **2-second focus dwell**, not on focus-enter,
to avoid a sound storm during shelf scanning; (2) audio defaults to
**muted** with an unmute affordance; (3) a global "reduce motion"
toggle in Settings disables both auto-play and `Carousel`
auto-advance; (4) `Carousel` auto-advance interval is **≥ 7 seconds
per slide** (W3C-APG floor is 5 s; HelixPlay picks 7 s for living-
room reading distance — see §H typography rationale); (5)
auto-advance pauses on focus and on D-pad movement; (6) the OS
`prefers-reduced-motion` (or the Android `Settings.Global.ANIMATOR_DURATION_SCALE = 0`
proxy) overrides the in-app toggle. tvOS enforces a similar
contract via `UIAccessibility.isReduceMotionEnabled`. Cross-link to
C11 Z-2 ("White-label motion-sensitivity opt-out").

maps to roughly 200 px at @1x scale — HelixPlay's tvOS card size is
larger still, 280 × 158 pt for landscape art (16:9). The shelf
("rail") pattern is the canonical horizontal grouping unit across
Netflix, Disney+, Apple TV, PS5, and Xbox dashboards: 12-column
grid with 52 dp columns + 20 dp gutters per Google's TV Design Kit;
the last visible item "peeks" past the right edge to signal more
content. Vertical density: 1 hero + 5–6 shelf rows visible on a
1080p layout; 1 hero + 6–7 rows on 4K. **Insight #6 reinforced:**
identical pattern across PS5, Xbox, Netflix, Disney+, Apple TV
constitutes the **scènes-à-faire** of the genre (see §I) — diverging
costs UX and may even invite trade-dress claims if combined with a
distinctive brand visual treatment. HelixPlay's white-label theming
must therefore preserve the shelf paradigm even at maximum brand
divergence.

*Apple Computer, Inc. v. Microsoft Corp.*, 35 F.3d 1435 (9th Cir.

console-dashboard pattern is unambiguously stock — used by Sony

focus-on-card hover effect, the auto-advancing hero carousel, and
the leftmost "All Games" library affordance — is therefore
defensible under the *scènes-à-faire* doctrine and merger doctrine
in the U.S., and under the EU equivalent (`InfoSoc Directive`
recital 9 + the *SAS Institute v. World Programming* CJEU C-406/10
holding that functional interface elements are not protected as
expression). **Insight #6 verdict:** validated. HelixPlay's MVP
landing screen is intentionally a console-dashboard clone at the
layout level; brand differentiation lives in colour, type, motion,
and content curation (per C11 white-label theming), not in layout
paradigm.

**Distilled findings.** Compose for TV runs at API 21+, but the
**memory and CPU envelope** on a typical 2024-vintage Amlogic S905X4
or MediaTek MT9602 (HelixPlay's lower bound TV-target SoC) is tight:
~ 1.5 GB RAM available to apps after the Android TV system reservation,
4 ARM Cortex-A55 cores at ~ 2.0 GHz, no Vulkan-class GPU. Q1 2026
field measurements (12 Android TV boxes) show MediaTek MT8696 holding
sub-200 ms input latency at 98 % frame completion in YouTube
playback; Rockchip RK3566 averages 92 %; Amlogic S922X drops to 84 %.
For HelixPlay on Compose for TV the budgets are: **16.6 ms / frame
@ 60 fps, 8.3 ms / frame @ 120 fps**; recomposition counts must stay
under ~ 100 per frame in a shelf-scroll; `LazyRow` items must use
stable keys; `derivedStateOf` is mandatory for all "is this row
focused" predicates to prevent recomposition cascades. Flutter on TV
(FlutterEmbedder Android TV variant) is the **fallback path** the
chapter prescribes for hardware where Compose for TV recomposition
profiling shows > 16 ms p95 frame time after optimisation; Flutter's
custom rendering engine delivers 60–120 fps on Android API 29+ with
~ 120 MB baseline memory footprint (vs ~ 80 MB Compose), but
eliminates shader compilation jank entirely. Network stack: **Cronet
is the canonical HTTP/3 + QUIC transport** for HelixPlay TV clients,
used via `cronet-transport-for-okhttp` so Retrofit / OkHttp call
sites are unchanged. ExoPlayer's `CronetDataSource` provides the
trailer-playback transport. OkHttp alone tops out at HTTP/2; the
HTTP/3 capability is only available through Cronet (or a third-party
QUIC implementation, but Cronet is the only Google-maintained
option in 2026). **Brotli compression** (per R-07) is set via
`Accept-Encoding: br, gzip` in the Cronet `UrlRequest` builder.
