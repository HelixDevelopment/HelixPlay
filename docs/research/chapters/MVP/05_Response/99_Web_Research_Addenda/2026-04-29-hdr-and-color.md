## §A — PQ (SMPTE ST 2084) + HLG (BT.2100) transfer functions

PQ and HLG are the two HDR transfer functions HelixPlay must carry end-to-end. PQ (Perceptual Quantizer, SMPTE ST 2084) was developed by Dolby and standardised by SMPTE in 2014; its 0–1 normalised range maps to absolute luminance values from 0 to 10 000 cd/m² (nits) via a non-linear curve derived from the Barten human-vision-banding model. HLG (Hybrid Log-Gamma, BT.2100 Rec. ITU-R) was jointly developed by BBC + NHK; its lower half is conventional gamma (SDR-compatible), and its upper half is logarithmic, giving relative-luminance HDR with no metadata required and natural SDR-display fall-through. C32 §3 codifies the per-path transfer-function ladder: PQ for "professional" HDR clients (Apple TV / consoles / HDR10-capable monitors), HLG for "broadcast-style" clients with mixed-fleet displays where graceful SDR fall-through is preferable, and BT.709 gamma 2.4 / sRGB for SDR-only clients with host-side or client-side tone-mapping (§D + §H).

## §B — HDR10 + HDR10+ + Dolby Vision metadata

HDR10 is the static-metadata baseline: SMPTE ST 2086 (mastering display colour volume — primaries, white point, max + min mastering luminance) plus CTA-861.3 (MaxCLL + MaxFALL — content light-level statistics). HDR10+ extends HDR10 with frame-/scene-level dynamic metadata defined by SMPTE ST 2094-40 (Color Volume Transform Application #4, developed by Samsung). Dolby Vision uses proprietary dynamic metadata at the L1..L11 metadata-level granularity, with the key streaming profiles being Profile 5 (IPT-PQ, no HDR10 fall-through), Profile 8.1 (HDR10 base layer + dynamic metadata, recommended for low-latency game streaming), and Profile 8.4 (HLG-base + dynamic metadata, broadcast-friendly). C32 §4 codifies the HelixPlay metadata-tier ladder: HDR10 is mandatory-emit when the host detects HDR10-capable client; HDR10+ is opt-in (host emits when client signals HDR10+ via EDID HDR Dynamic Metadata Data Block — §E); Dolby Vision is **out-of-scope for HelixPlay MVP** because consumer GPU encoders (NVENC, AMF, QSV) cannot natively generate Dolby Vision RPU (Reference Picture Unit) metadata in real-time, only x265 software encode supports Profile 5 / 8.1 / 8.2 (and even that is computationally too expensive for 4K60 game streaming).

## §C — RTP extension carriage for HDR metadata over WebRTC

WebRTC carries HDR metadata via the experimental RTP header extension at `http://www.webrtc.org/experiments/rtp-hdrext/color-space`, defined in the WebRTC source tree but not yet IETF-standardised. The 28-byte payload encodes ITU-T H.273 colour-primaries / transfer / matrix / range identifiers in bytes 0–3, mastering-display luminance (max in nits + min in 1/10 000 nits) in bytes 4–7, CIE 1931 xy chromaticity coordinates for R / G / B / white-point (each scaled by 50 000) in bytes 8–19, and MaxCLL + MaxFALL (each in nits) in bytes 20–23. The extension MUST appear only in the last RTP packet of each video frame to mark the frame boundary. WebRTC's color-space extension carries enough metadata for HDR10 static delivery; HDR10+ dynamic metadata + Dolby Vision RPU MUST go inside the elementary bitstream as SEI (HEVC) or OBU (AV1) blocks rather than RTP-extension fields, because the per-frame metadata payload exceeds the RTP-extension byte-budget and the cadence is too fast for header-extension scheduling.

## §D — Client-side tone-mapping (Insight #3 asymmetric optimisation)

Client-side tone-mapping is the asymmetric-optimisation strategy: the host emits one HDR-canonical bitstream (HDR10 base, HEVC Main 10 or AV1 Main 10), and any client whose display does not support PQ + BT.2020 + HDR10 metadata performs a GPU-accelerated tone-map post-decode to land the signal in BT.709 + sRGB / gamma-2.4 SDR. The reference algorithms are Hable (Uncharted 2 filmic curve), ACES Filmic Tone Mapping (Narkowicz 2015 simplified curve), Reinhard (simple division-based curve), Uchimura (Gran Turismo curve), and the BT.2390 EETF (ITU-R standard, Hermite-spline roll-off — the libplacebo default). HelixPlay clients ship with libplacebo for GPU-accelerated tone mapping (Vulkan + GLES on desktop / Android; Metal-via-MoltenVK on Apple). Client-side tone-mapping costs ~0.5–2 ms per frame on a discrete GPU and ~3–8 ms on integrated mobile GPUs — well within the per-frame budget given Insight #6's 30–100 ms display-pipeline latency dominates anyway.

## §E — EDID HDR Static Metadata Block (CTA-861.3 capability detection)

EDID (Extended Display Identification Data, VESA E-EDID 1.4) carries the HDR Static Metadata Data Block defined in ANSI/CTA-861.3 (originally CTA-861-G; extended through CTA-861-H). The block advertises which EOTFs the display supports (Traditional gamma SDR-luminance; Traditional gamma HDR-luminance; SMPTE ST 2084 PQ; Hybrid Log-Gamma BT.2100), plus the desired-content-max-luminance, max-frame-average-luminance, and min-luminance per the display's EDID-declared mastering envelope. CTA-861.3 + CTA-861-H also specify the HDR Dynamic Metadata Data Block (HDR DMM Data Block) that advertises HDR10+ (IEEE OUI 90:84:8B = HDR10+ Technologies LLC) and Dolby-Vision-style dynamic metadata support. HelixPlay's host agent and Wails / Flutter / Angular clients call into libdisplay-info (Wayland-native) / DXGI-IDXGIOutput6 (Windows) / IORegistry CGDisplayCopyColorSpace (macOS) / SDL HDR API (cross-platform) to extract the per-display HDR capability profile and feed it into the negotiation chain (§I).

## §F — BT.2020 vs BT.709 colour spaces

BT.709 (Rec. ITU-R BT.709) is the SDR colour space — primaries at the (0.64, 0.33), (0.30, 0.60), (0.15, 0.06) corners of CIE 1931, D65 white point, gamma ~2.4, 8-bit colour depth nominal. BT.709 covers ~35.9 % of the CIE 1931 visible-light gamut. BT.2020 is the wide-gamut HDR colour space — primaries at the corners (0.708, 0.292), (0.170, 0.797), (0.131, 0.046) — which are pure spectral wavelengths reachable only by lasers — D65 white point, supporting 10-bit + 12-bit colour depth. BT.2020 covers ~75.8 % of CIE 1931. BT.2020 is mandatory for HDR10 / HDR10+ / Dolby Vision / HLG; HelixPlay's host emits BT.2020 primaries on the HDR path and BT.709 on the SDR path; client-side gamut mapping (BT.2020 → BT.709 via ITU-R BT.2407 method) is paired with the tone-mapping ladder (§D) when the client display is BT.709-only. P3-D65 (Display P3, Apple's native consumer space, ~25 % wider than sRGB / BT.709) is the practical wide-gamut envelope for most consumer HDR displays in 2026 — BT.2020 corner coverage is a future-target, not a currently-shipped consumer-display capability.

## §G — 10-bit vs 12-bit color depth (HEVC Main 10 / AV1 Main 10 / AV1 Professional)

10-bit is the HDR floor. ## §H — HDR codec interaction (HEVC + AV1 hardware)

HEVC + AV1 are the two viable HDR codecs for HelixPlay. HEVC carries HDR via SEI messages (`mastering_display_colour_volume` SEI for SMPTE ST 2086 + `content_light_level_info` SEI for CTA-861.3 + `user_data_registered_itu_t_t35` SEI for HDR10+ / Dolby Vision dynamic metadata). AV1 carries HDR via metadata OBUs (`metadata_hdr_mdcv` for mastering display + `metadata_hdr_cll` for content light level + `METADATA_TYPE_ITUT_T35` OBU for HDR10+). H.264 (AVC) is fundamentally limited for HDR — 8-bit-only on consumer hardware (the High 10 profile exists but has near-zero hardware-decoder market presence), no native HDR-metadata mechanism. Blackwell-NVENC's 10-bit H.264 path (§A8 of the codec-selection addendum) is encode-only and lacks the SEI plumbing for HDR10/HDR10+ metadata in any standardised way. C32 §7 codifies the HDR-codec ladder: HDR10 + HDR10+ on AV1 (premium tier) → HDR10 + HDR10+ on HEVC Main 10 (standard tier) → SDR-only on H.264 (universal fallback, with host-side or client-side tone-mapping per §D + §H).

## §I — Display latency floor (Insight #6) + HDR negotiation chain

Insight #6 is binding for C32: after capture / encode / transport / decode are optimised, the residual unaddressed latency is the **display pipeline** — 30–100 ms of internal processing on consumer TVs (motion smoothing, edge sharpening, dynamic contrast, scaler / deinterlacer, frame interpolation). HDMI 2.1 ALLM (Auto Low Latency Mode, CTA-2071) is the HDMI-Forum signal that lets a source device tell the sink "this is interactive content, please disable processing." With ALLM engaged + game-mode active, modern OLED displays (LG C5, Samsung S95F, Sony A95L) report 4.7–10 ms input lag; without ALLM, the same display can report 50–100 ms lag. The HDR-negotiation-chain spans: source-device colour / luminance / metadata capability → HDMI-cable bandwidth class (FRL 8 / 10 / 12 Gbps for HDMI 2.1) → optional in-line AVR / extender / matrix / capture device → display EDID-advertised HDR Static + Dynamic Metadata Data Blocks → displayed-content metadata via HDR Dynamic Metadata Extended InfoFrame. Any link in the chain that does not faithfully forward HDR metadata + ALLM signalling causes the negotiation to collapse to SDR + non-game-mode, blowing the latency budget. HelixPlay's host agent emits the ALLM bit in the HDMI InfoFrame and re-asserts on every session start; the client UI exposes a "TV game-mode advisor" that detects + warns when the chain reports degraded HDR / ALLM state.
