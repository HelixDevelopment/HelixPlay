## §A NVENC dual-session orchestration (SDK 12 / 13)

NVIDIA's Video Codec SDK 12 (Lovelace baseline, 2022-Q4) and SDK 13 (Blackwell, 2025-Q1) expose dual-session encoding as a first-class pattern: each `NvEncOpenEncodeSessionEx` returns an independent encoder context with its own `NV_ENC_CONFIG` (preset, tuning, rate-control mode, target bitrate, GOP length, IDR period, B-frame depth, lookahead, AQ strength), and the NVENC hardware schedules the two sessions onto the available NVENC engines (1 on RTX 4060 / 4070 / 5050 / 5060 / 5070, 2 on RTX 4070 Ti / 4080 / 4080 Super / 5070 Ti / 5080, 3 on RTX 5090, plus 1 NVENC + 1 NVDEC on RTX 4090, 2 NVENC + 2 NVDEC on RTX PRO 6000 Blackwell). The driver's NVENC scheduler load-balances across engines transparently — applications do not need explicit affinity APIs. The 2025 consumer-driver session-limit value is **8 simultaneous encode sessions** (lifted from the prior 5-session ceiling in early 2024 by the R555+ driver line; some 2025-Q4 sources cite 12 on the latest R580 LTS). HelixPlay's C29 §3 binds the streaming session to `P4 + tuningInfo = NV_ENC_TUNING_INFO_ULTRA_LOW_LATENCY + rateControlMode = NV_ENC_PARAMS_RC_CBR + frameIntervalP = 1 (P-only GOP) + idrPeriod = 60 + lookaheadDepth = 0` and the recording session to `P5 or P6 + tuningInfo = NV_ENC_TUNING_INFO_HIGH_QUALITY + rateControlMode = NV_ENC_PARAMS_RC_VBR + frameIntervalP = 4 (P + 3 B) + idrPeriod = 240 + lookaheadDepth = 8`. The two sessions consume the same input texture via `NV_ENC_INPUT_RESOURCE_TYPE_DIRECTX` (Windows) / `NV_ENC_INPUT_RESOURCE_TYPE_CUDADEVICEPTR` (CUDA / Linux) registered into both encoders' input registries — no GPU-memory copy is required.

## §B AMD AMF dual-session (no session limits, RDNA3 / RDNA4)

AMD's Advanced Media Framework (AMF) SDK + RDNA3 (RX 7000, VCN 4.0) + RDNA4 (RX 9000, VCN 5.0) expose dual-session encoding without any artificial consumer-driver session ceiling — AMD's competitive response to NVIDIA's historical 3 / 5 / 8-session limit. The AMF SDK exposes six usage modes (`AMF_VIDEO_ENCODER_USAGE_TRANSCODING`, `_ULTRA_LOW_LATENCY`, `_LOW_LATENCY`, `_WEBCAM`, `_HIGH_QUALITY`, `_LOW_LATENCY_HIGH_QUALITY` / HQLL); each spawned `AMFComponent` instance is independently parameterised. AMF SDK 1.4.35 introduced the multi-HW-instance encoder mode that explicitly enables routing distinct encoder instances onto distinct VCN media engines on dual-engine SKUs (RX 7900 XT / 7900 XTX on RDNA3; RX 9070 / 9070 XT on RDNA4). RDNA4's VCN 5.0 also adds AV1 B-frame support (the RDNA3 VCN 4.0 engine encoded AV1 with I + P frames only) and delivers +25% H.264 LL quality + +11% HEVC quality + +50% AV1 / VP9 decode throughput vs RDNA3. HelixPlay's C29 §4 binds the AMF streaming session to `Usage = ULTRA_LOW_LATENCY + LOWLATENCY_MODE = true + QualityPreset = SPEED + MaxConsecutiveBPictures = 0 + RateControlMethod = CBR_LATENCY_CONSTRAINED + EnforceHRD = true` and the recording session to `Usage = HQLL + QualityPreset = QUALITY + MaxConsecutiveBPictures = 3 + RateControlMethod = LATENCY_CONSTRAINED_VBR (LCVBR)` — distinct `AMFComponent` instances created against the same `AMFContext` so they share the captured texture without GPU-memory copy.

## §C Intel QSV / oneVPL dual-session (no theoretical session limits, Battlemage)

Intel's Quick Sync Video (QSV) hardware-encoder line in 2026 spans the Arc Battlemage discrete line (Arc B580, B570, B770) and the Xe2 integrated GPU line (Lunar Lake, Arrow Lake, Panther Lake). The legacy MediaSDK API is fully superseded by oneVPL (the Intel Video Processing Library, now `Intel® VPL`). The 2025 oneVPL 2.13 release adds initial Battlemage support + AI-based Super Resolution. The architectural constraint is that **one `mfxSession` can host only one component of each type** (one decode + one VPP + one encode); to spawn two encoder instances, the application creates two distinct `mfxSession` handles via `MFXLoad` + `MFXCreateSession`, with each session holding its own `MFXVideoENCODE_*` component. Sessions can share input surfaces via `mfxFrameSurface1` references when allocated from a system or video-memory allocator both sessions are bound to. **There is no theoretical concurrent-session limit on Intel iGPU or Arc dGPU** — Intel does not artificially gate concurrent encodes the way NVIDIA's consumer driver does. The async pipeline depth (`AsyncDepth` parameter, default 4) controls per-session parallelism; for the streaming branch HelixPlay binds `AsyncDepth = 1` (frame-by-frame submission, lowest latency) + `TargetUsage = TU7` (`MFX_TARGETUSAGE_BEST_SPEED`) + `RateControlMethod = MFX_RATECONTROL_CBR` + `GopRefDist = 1` (P-only) + `LowDelayBRC = ON`; for the recording branch `AsyncDepth = 4` + `TargetUsage = TU4` (`MFX_TARGETUSAGE_BALANCED`) + `RateControlMethod = MFX_RATECONTROL_VBR` + `GopRefDist = 4` (1 B-frame between P-frames or 3 with `BRefType = MFX_B_REF_PYRAMID`) + `ExtendedPicStruct = MFX_PICSTRUCT_PROGRESSIVE`. The same `mfxSurfaceArray` zero-copy pool feeds both encoders.

## §D Frame-Tee fan-out pattern (zero-copy, GPU-native)

The Frame-Tee fan-out pattern is the C29 chapter's binding architectural primitive: a single capture-stage produces one frame per VBLANK; the Frame-Tee distributes a **reference** (not a copy) of that frame to two encoder sessions. The reference primitive is OS / API specific: **DMA-BUF FD** on Linux (Wayland `ext-image-copy-capture-v1` + PipeWire DMA-BUF zero-copy + KMS `addfb2`); **`ID3D11Texture2D` keyed-mutex shared resource** on Windows (DXGI Desktop Duplication API + `IDXGIResource1::CreateSharedHandle`); **`IOSurfaceRef`** on macOS (ScreenCaptureKit + IOSurface-backed `CMSampleBuffer`); **`CUarray` / `CUmemoryPool` allocation** on the NVENC CUDA path. The reference-counting semantics ensure the frame is held alive until both encoders signal completion. GStreamer's `tee` element is the canonical reference implementation: it duplicates buffer references across multiple branches, with each branch running its own queue + thread to avoid one branch stalling the other. NVIDIA Jetson's NVMM memory + DMA-BUF integration is the production-grade reference for the zero-copy pattern: capture → tee → branch-1 (NVENC streaming) + branch-2 (NVENC recording), all without a single CPU-side memory copy. The C29 §3 specification binds the Linux capture path to PipeWire DMA-BUF + GStreamer `tee` (or hand-rolled equivalent in Go) with two `nvv4l2h264enc` / `vaapih265enc` / `qsvh265enc` branches; the Windows path to DXGI shared resources fed into both NVENC / AMF / oneVPL sessions; the macOS path to IOSurface fed into two `VTCompressionSession` instances.

## §E Per-encoder bitrate / preset / GOP / B-frame divergence

The per-encoder configuration divergence is the second-order benefit of the dual-session pattern: streaming and recording have fundamentally different optimisation targets, and a single shared-encoder topology (e.g. an FFmpeg `tee` muxer that fans out the **same** encoded bitstream to two destinations) cannot exploit them. Streaming is bound by (a) link upload bandwidth (CBR-bounded), (b) end-to-end latency (P-only GOP, no B-frames, no lookahead, ULL tuning), (c) decoder-compatibility (H.264 baseline / main, HEVC main, AV1 main), (d) packet-loss resilience (short IDR period, frequent keyframes, intra-refresh). Recording is bound by (a) storage bandwidth (NVMe write IOPS, typically 1-3 GB/s on consumer SSDs), (b) post-edit workflow (B-frames + lookahead acceptable; quality-per-byte matters more than wall-clock latency), (c) archive compatibility (HEVC main10 / AV1 main / future VVC), (d) crash safety (fragmented containers, frequent metadata flushes). HelixPlay's C29 §4 codifies the streaming-vs-recording bifurcation per vendor: NVENC `P4 + ull + cbr + b-frames=0 + idrPeriod=60` (streaming) vs `P5/P6 + hq + vbr + b-frames=3 + idrPeriod=240 + lookahead=8` (recording); AMF `ULTRA_LOW_LATENCY + SPEED + CBR + b-frames=0` (streaming) vs `HQLL + QUALITY + LCVBR + b-frames=3` (recording); oneVPL `TU7 + CBR + GopRefDist=1 + low_delay_brc=on + AsyncDepth=1` (streaming) vs `TU4 + VBR + GopRefDist=4 + AsyncDepth=4` (recording). The two encoders consume the same input frame and produce independent bitstreams.

## §F Thermal headroom budget (Insight #1)

**Insight #1 — The "Thermal Wall" Is the Hidden Bottleneck for Dual-Path Encoding** (HIGH confidence) is the binding architectural risk for C29. Dual encoding adds 15-25 W of GPU power draw (NVENC ASIC + NVDEC + memory-bandwidth headroom for two simultaneous encoder pipelines); on a thermally constrained GPU, this can push the die into the 83 °C thermal-throttle zone (the standard NVIDIA throttle threshold for desktop GeForce — RTX 2080 Super = 84 °C, RTX 30/40/50 = 83 °C nominal with hotspot-temperature spikes triggering earlier throttling on poorly cooled cards). When the throttle engages, **both** stream and record quality drop simultaneously: clock speeds reduce by 10-25%, NVENC throughput drops 25-30%, and the encoder either drops frames or reduces effective bitrate. The C29 §6 binding is a **proactive thermal-aware quality reduction loop**: a Go goroutine reads GPU temperature every 1 second via NVML (`nvmlDeviceGetTemperature`), ROCm-SMI (`rsmi_dev_temp_metric_get`), Intel `xpu-smi` (`xpu-smi stats`), or Apple `powermetrics` (`powermetrics --samplers gpu_power`); when temperature crosses a configurable warning threshold (default 78 °C — 5 °C below the 83 °C throttle to leave hysteresis), the loop reduces the **recording** branch quality preset by one step (`P5 → P4` on NVENC; `QUALITY → BALANCED` on AMF; `TU4 → TU5` on oneVPL) and target bitrate by 20% via `NV_ENC_RECONFIGURE_PARAMS` / `AMF_VIDEO_ENCODER_RATE_CONTROL_*` / `mfxEncodeCtrl`. The streaming branch is **not** modified — its latency contract is the binding user-visible SLA. Frame pacing via NVIDIA Reflex (or AMD Anti-Lag, Intel Xe Low-Latency) reduces the GPU render workload by capping frame-rate to the display refresh, freeing thermal headroom for the encoder pipeline.

## §G Recording-side codec / container choice

The recording-side codec / container choice diverges from streaming because the optimisation targets are different (§E). HelixPlay's C29 §5 binds the recording codec to **HEVC (H.265 main10) by default** and **AV1 (main 10-bit) when available** (RDNA4 VCN 5.0 with AV1 B-frame support; Lovelace + Blackwell NVENC; Arc Battlemage QSV; Apple M5+ VideoToolbox); **H.264 high profile** is the fallback when HEVC / AV1 hardware encode is unavailable on the recording branch. The container is **fragmented MP4 (fMP4)** by default (HLS-compatible, fragment-decodable on partial-write, broad post-edit tool compatibility) with **MKV (Matroska)** as an alternative for crash-safety-paranoid deployments (no `moov` atom finalisation required — the file is playable up to the point of interruption even if the recorder crashes mid-write). The 2026 codec-efficiency baseline is HEVC ≈ 50% bitrate of H.264 at the same quality; AV1 ≈ 50-70% bitrate of H.264 (20-30% better than HEVC). The recording branch budgets typically run 25-40 Mbps for HEVC 1080p60 main10, 40-80 Mbps for HEVC 4K60 main10, 18-30 Mbps for AV1 1080p60, 30-60 Mbps for AV1 4K60 — versus 6-12 Mbps for the streaming branch H.264 / HEVC 1080p60 over WebRTC (link-bandwidth-bounded, not quality-bounded). Local-NVMe write throughput at these budgets is well within consumer SSD capacity (1-3 GB/s sequential-write headroom).

HelixPlay's C29 + C30 + C31 (capture → dual-path encode → multi-backend storage with SMB / NFS / FTP / WebDAV / object-store) realises the "DVR for your gaming PC" feature set that no competitor offers. The Sunshine architecture is HelixPlay's implementation baseline (C28 explicitly tracks the Sunshine++ pattern); C29 extends it with the second encoder branch + recording pipeline.

## §Z Contradictions index

This index records the points where the 2026 evidence collected in §A–§I diverges from the 2024 / early-2025 baseline in [`video-tech_dim04.md`](../../03_video_technology/02_Response/Agent_Results/research/video-tech_dim04.md) (1,013 lines) or sharpens an open conflict in [`video-tech_cross_verification.md`](../../03_video_technology/02_Response/Agent_Results/research/video-tech_cross_verification.md).

- **Z-1 — NVENC consumer-driver session-limit value.** `video-tech_dim04.md` §1 records the historical 3 / 5-session limit on consumer GeForce drivers. 2026 evidence (A3 + A4 + A5 + A6) **sharpens** the post-2024-Q1 value to **8** simultaneous sessions; some 2025-Q4 sources (A4) cite 12 on the latest R580 LTS. C29 §3 codifies the 8-session ceiling as the binding consumer-driver constraint, with the legitimate RTX PRO / Quadro / datacenter L4 / L40S / RTX PRO 6000 path that lifts it.
- **Z-2 — Tee muxer vs Frame-Tee terminology.** `video-tech_dim04.md` §1.2 documents the FFmpeg tee muxer pattern as a single-encode-multi-output primitive (A2 in dim04). 2026 evidence (D1 + D2 + D6) **distinguishes** the FFmpeg `tee` muxer (single encoded bitstream → multiple output formats / files) from the GStreamer `tee` element (single uncompressed frame → multiple independent encoders). HelixPlay's C29 §3 binding is the **GStreamer-style Frame-Tee** (uncompressed-frame fan-out → two independent encoders with divergent presets / bitrates / GOPs), **not** the FFmpeg-style tee muxer (which would force the same encoded bitstream into both destinations and lose the per-branch optimisation benefit codified in §E). The distinction is sharpened, not contradicted, by 2026 evidence.
- **Z-3 — AMF multi-HW-instance encoder mode availability.** `video-tech_dim04.md` §2.2 records AMF's per-encoder configuration but does not specifically address multi-HW-instance routing on dual-VCN SKUs. 2026 evidence (B2 + B3) **adds** the multi-HW-instance encoder mode introduced in AMF SDK 1.4.35, which explicitly routes distinct encoder instances onto distinct VCN media engines on RX 7900 XT / 7900 XTX / RX 9070 / 9070 XT. C29 §4 codifies this as the binding routing primitive on dual-engine AMD SKUs.
- **Z-4 — Intel concurrent-session ceiling.** `video-tech_dim04.md` §2.3 documents Intel QSV's no-theoretical-limit posture qualitatively. 2026 evidence (C3 + C6 + C7) **quantifies** the practical envelope: 2-8 simultaneous transcodes per iGPU + scaling on Arc dGPU. C29 §6 codifies the per-SKU practical capacity envelope, with thermal headroom (Insight #1) as the binding constraint above the theoretical no-limit posture.
- **Z-5 — Recording container preference.** `video-tech_dim04.md` §3 documents both fMP4 and MKV as crash-safe options without a strong default preference. 2026 evidence (G1 + G2 + G3 + G9) **sharpens** the practitioner default to **fMP4** for HLS / DASH / post-edit compatibility and **MKV** as the crash-safety-paranoid alternative with remux-to-MP4 on close. C29 §5 codifies fMP4-default + MKV-alternative.
- **Z-6 — Recording-codec efficiency baseline.** `video-tech_dim04.md` §4 documents H.264 / HEVC efficiency without specific 2026 AV1 numbers. 2026 evidence (G5 + G6 + G7) **adds** the AV1 20-30% efficiency lead over HEVC and the 5-8x slower AV1 hardware-encode speed vs HEVC. C29 §5 codifies HEVC-default + AV1-where-available + H.264-fallback for the recording branch.
- **Z-7 — Sunshine multi-session limit removal.** `video-tech_dim04.md` does not specifically address Sunshine's session-limit posture. 2026 evidence (I3 + I4) **adds** that Sunshine's "session-limit removal" applies to multiple clients on the **same** stream, not to multiple independent recording sessions. C29 §7 codifies this distinction as the architectural gap HelixPlay fills (Insight #10).
- **Z-8 — NVENC GOP-immutability constraint.** `video-tech_dim04.md` does not specifically call out the NVENC SDK constraint that `gopLength` / `idrPeriod` / `frameIntervalP` cannot be reconfigured mid-session. 2026 evidence (A1) **adds** this constraint, which forces HelixPlay's C29 §3 to either (a) tear down + recreate the encoder when the operator changes recording-side GOP structure, or (b) freeze the GOP at session-start. C29 §6 codifies (b) for the streaming session and (a) for the recording session (acceptable because tearing down + recreating the recording encoder mid-session loses at most one GOP of footage at the boundary).

None of the contradictions overturn the core C29 dual-path encoding contract or the binding insights (#1, #4, #10). They resolve into per-clause precisions the chapter codifies inline.
