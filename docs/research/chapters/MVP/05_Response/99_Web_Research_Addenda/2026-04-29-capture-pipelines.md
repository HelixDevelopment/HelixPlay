## §A Wayland screencopy + screencast portals (2026)

The Linux capture surface in 2026 is the convergence of three protocols: **(1)** the legacy `wlr-screencopy-unstable-v1` protocol (wlroots-only, the previous-generation primitive used by Sway / Hyprland / River / Niri compositors); **(2)** the new `ext-image-capture-source-v1` + `ext-image-copy-capture-v1` Wayland staging protocols merged into the Wayland Protocols repository in 2024-Q4 after nearly three years of design (the cross-compositor replacement for `wlr-screencopy` that explicitly supports DMA-BUF + per-frame buffer constraints + cursor isolation); **(3)** the `org.freedesktop.portal.ScreenCast` xdg-desktop-portal interface that mediates capture access through a permission prompt and exports the frames over PipeWire — universally supported across all major desktop-focused Wayland compositors (KWin / Mutter / wlroots-based). HelixPlay's C28 §3 binds the Linux capture backend ladder as: **(a)** prefer the xdg-desktop-portal `ScreenCast` portal when running unprivileged (permission-prompted, sandbox-friendly, the only path that works under Flatpak / Snap); **(b)** prefer the `ext-image-copy-capture-v1` staging protocol when the compositor exposes it (lower latency, no portal-dialog, headless-friendly); **(c)** fall back to `wlr-screencopy-unstable-v1` on wlroots compositors that have not adopted `ext-image-copy-capture-v1` yet; **(d)** fall back to `kmsgrab` (DRM master KMS plane capture) only when no Wayland-native path is available and the operator has explicit consent — KMS capture requires privileged DRM master access and conflicts with HDR on most consumer drivers (Sunshine treats KMS as the HDR-required path on Linux because NVFBC + X11 do not support HDR).

## §B DXGI Desktop Duplication API + Windows 11 24H2 quirks

The Windows capture surface in 2026 is the bifurcation of two primitives: **(1)** the legacy DXGI Desktop Duplication API (`IDXGIOutputDuplication::AcquireNextFrame`, exposed via `dxgi1_2.h` since Windows 8) — the path Sunshine + Moonlight + Parsec have used since 2018 because it ships in every Windows 10 / 11 SKU and works without a per-app permission prompt; **(2)** the modern Windows Graphics Capture (WGC) API (`Windows.Graphics.Capture.GraphicsCaptureItem`, exposed via WinRT since Windows 10 1803) — Microsoft's recommended replacement, cross-GPU, sandbox-friendly, but with a permission-prompt UX and a yellow capture border that the OS draws over the captured surface (toggleable via `GraphicsCaptureSession::IsBorderRequired` only on Windows 11 21H2+). The 2026 quirk that drives HelixPlay's C28 §5 backend selection is the **Windows 11 24H2 MPO regression**: 24H2 changed how the Desktop Duplication API interacts with Multiplane Overlay (MPO) hardware composition, making DXGI heavily reliant on MPO support to distinguish frame updates correctly when a foreground game window and a captured-display window overlap. On systems without MPO support (older / underpowered drivers), DXGI's frame-pacing on 24H2 is unreliable. The KB5046617 update (2024-11) restored partial reliability but did not eliminate the problem. HelixPlay's C28 §5.3 binds the Windows backend ladder as: **(a)** prefer WGC when the host is Windows 11 24H2 + the GPU driver advertises MPO; **(b)** prefer DXGI Desktop Duplication on Windows 10 / Windows 11 23H2 and earlier; **(c)** keep both backends instantiable at runtime so the capture process can hot-switch on `DXGI_ERROR_ACCESS_LOST` (the common UAC-elevation / monitor-hot-plug / portrait-rotation failure mode).

## §C IOSurface + ScreenCaptureKit on macOS 14 Sonoma + 15 Sequoia

The macOS capture surface in 2026 is unified on **ScreenCaptureKit** (introduced macOS 12.3, matured macOS 13 Ventura, refined macOS 14 Sonoma, fully GPU-accelerated macOS 15 Sequoia). ScreenCaptureKit replaces `CGDisplayStream` (deprecated since macOS 12.3) and `CGWindowListCreateImage` (deprecated since macOS 12.3) with a modern async / permission-aware API that gives per-frame control over content filter (`SCContentFilter`), stream configuration (`SCStreamConfiguration`), and stream output (`SCStreamOutput`). The defining 2026 capability for HelixPlay's C28 §6 binding is **IOSurface zero-copy GPU texture access**: every `CMSampleBuffer` delivered by `SCStream` wraps a `CVPixelBuffer` backed by an `IOSurface` (queryable via `CVPixelBufferGetIOSurface`), which can be bound directly to a Metal texture via `MTLDevice.makeTexture(descriptor:iosurface:plane:)` — any modification to the IOSurface contents propagates to the Metal texture without copying. The defining 2026 features in macOS 14 / 15 are: **(a)** `SCScreenshotManager` (still-image API on the same content-filter primitives); **(b)** `SCContentSharingPicker` (system-level picker UI for sharing windows / displays, introduced macOS 14); **(c)** ProRes capture support via `SCStreamConfiguration.captureResolution = .best`; **(d)** `SCStreamConfiguration.queueDepth` (default 3, max 8) — the SPSC ring depth at the OS-API level that HelixPlay's C28 §3 frame-event publisher consumes; **(e)** `minimumFrameInterval` (CMTime) that lets the capture process opt out of capturing every VBLANK if the encoder cannot keep up. HelixPlay's C28 §6.4 binds the macOS capture configuration as: `pixelFormat = kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange`, `colorSpaceName = kCGColorSpaceSRGB` for SDR or `kCGColorSpaceITUR_2100_HLG` for HDR, `queueDepth = 3` (matched to C15 §3 SPSC ring depth), `minimumFrameInterval = CMTime(value: 1, timescale: refreshRate)`, `showsCursor = configurable`, `capturesAudio = true` (system audio capture introduced macOS 13).

## §D NVFBC (NVIDIA Frame Buffer Capture) — licensing + capability

NVIDIA Frame Buffer Capture (NVFBC) is NVIDIA's hookless, GPU-resident screen-capture API exposed via the NVIDIA Capture SDK. The 2026 licensing posture is the conjunction of three constraints: **(1)** NVFBC has been **deprecated on Windows since 2018** — the Windows-supported version is frozen at Capture SDK 7.1, which only works on Windows 10 1803 (build 17134); the Windows replacement is DXGI Desktop Duplication (Microsoft's recommended path) or NVIDIA's NvAPI extensions; **(2)** NVFBC remains **fully supported on Linux** through the NVIDIA Capture SDK and the proprietary NVIDIA driver — the X11-resident `NvFBC` library + the `NvIFR` in-process variant are still shipped; **(3)** consumer GeForce drivers **disable NVFBC by default** — only Quadro / RTX A-series / RTX PRO / Tesla / datacenter SKUs receive an NVFBC-enabled driver; the legitimate path to enable NVFBC on consumer SKUs requires the operator to install Quadro / Studio drivers that NVIDIA only licenses for those SKUs (the `keylase/nvidia-patch` project documents the binary patch approach but is not a legal redistribution path HelixPlay uses). The defining 2025 development is the Sunshine v2025.1.18 release that **eliminated the need for driver patching** — Sunshine implemented an alternative DRM/KMS-based capture path that achieves equivalent latency without requiring NVFBC, freeing consumer GeForce users from the licensing constraint. HelixPlay's C28 §7 binds the Linux NVIDIA capture path as: **(a)** prefer NVFBC when the operator's driver advertises NVFBC support (Quadro / RTX PRO / Studio); **(b)** fall back to PipeWire DMA-BUF + portal capture (the licensing-clean path); **(c)** never ship the `nvidia-patch` binary; **(d)** never bundle NVFBC-licensed binaries that the operator's driver does not legally allow. The C28 §7.3 capability detector tests `NvFBCCreateContext` at runtime and records the NVIDIA driver branch (R570 Blackwell / R580 LTS) to predict NVFBC availability.

## §E PipeWire Wayland integration (DMA-BUF zero-copy)

PipeWire is the multimedia routing daemon that mediates Wayland screencast capture in 2026. The defining capability for HelixPlay's C28 §3 binding is **DMA-BUF zero-copy buffer sharing** with explicit GPU synchronization fences: the PipeWire screencast stream exports the captured frames as DMA-BUF file descriptors that can be imported directly into the encoder process's GPU context (NVENC / VA-API / VDPAU / Metal-via-MoltenVK) without any CPU-side memcpy. The negotiation flow is **(1)** the PipeWire client requests `SPA_DATA_DmaBuf` data type via the format negotiation; **(2)** the compositor (the screencast portal's PipeWire node) advertises its supported DRM modifiers (linear, LINEAR-MOD, vendor-specific tiled formats); **(3)** the client picks a modifier that matches its encoder's import path (NVENC accepts linear + NV12-tiled; VA-API accepts linear + Y_TILED + Y_TILED_GEN12). The 2026 PipeWire stability story is the maturation of the explicit-sync extension (Wayland's `linux-explicit-synchronization-v2` + the matching PipeWire fence-passing) — without it, the encoder would have to insert a glFinish / vkDeviceWaitIdle to ensure the captured buffer's GPU writes are flushed; with it, the fence is passed alongside the buffer and the encoder waits on the GPU side. HelixPlay's C28 §3.6 binds the PipeWire integration as: **(a)** require PipeWire >= 0.3.84 (the version that stabilised explicit-sync for screencast); **(b)** require Mesa >= 24.0 + `EGL_EXT_image_dma_buf_import_modifiers`; **(c)** require the kernel >= 6.6 for stable DMA-BUF heap support; **(d)** fall back to mmap-based SHM transfer when DMA-BUF negotiation fails (the slow path that loses the zero-copy property).

## §F Sunshine++ pattern (cloudgaming Insight #1 — capture-process isolation)

The Sunshine++ pattern is the C28 §2 architecture spine: HelixPlay extends Sunshine's open-source capture-and-encode host agent with **(a)** capture-process isolation (the capture runs in its own OS process under a least-privileged user account, communicates with the parent agent over a Unix socket / Windows named pipe, exits cleanly on capture failure without taking down the parent agent); **(b)** frame-event publishing through a shared-memory SPSC ring (C15 §3) — the capture process is the producer, the encoder process is the consumer, no kernel-mediated context switch on the hot path; **(c)** multi-backend abstraction at the per-OS layer described in §A–§E + §G; **(d)** capability detection at startup that records the OS / GPU / display / driver version and selects the optimal capture path; **(e)** a hot-restart path that lets the capture process die and respawn without the encoder noticing (the SPSC ring tolerates a producer-side stall by backpressure on the encoder side, which is far better than the encoder dying on stale frames). The Sunshine v2025.1.18 release marks the GA point where the upstream Sunshine project absorbed many Sunshine++ posture improvements (the licensing-clean path, the multi-GPU eGPU posture, the DRM device identification logic). HelixPlay's C28 §2.4 binds the Sunshine++ pattern as: **(a)** consume Sunshine v2025.1.18+ as the upstream baseline and contribute fixes upstream rather than forking; **(b)** add the shared-memory SPSC ring as the IPC primitive (Sunshine still uses in-process channels, the architectural delta HelixPlay justifies on the cross-process isolation grounds); **(c)** make the capture-process ABI versioned (HelixPlay's host-agent + capture-process version negotiation at startup).

## §G Anti-cheat-aware capture (capture-detection avoidance)

The 2026 anti-cheat surface that affects HelixPlay's C28 §9 binding is the conjunction of three kernel-mode anti-cheat systems: **(1)** Riot Vanguard (Valorant, kernel driver loaded at boot), **(2)** Easy Anti-Cheat / EAC (Epic Games, kernel driver loaded at game launch — Fortnite, Apex Legends, Dead by Daylight, Rust, The Finals), **(3)** BattlEye (kernel driver loaded at game launch — PUBG, Rainbow Six Siege, ARMA, DayZ, Battlefield 6). These systems use **(a)** memory-signature scanning, **(b)** window enumeration (looking for cheat-overlay window names), **(c)** hardware fingerprint reading (motherboard / disk / MAC / GPU IDs), **(d)** kernel-callback registration to detect process-injection / DLL-injection. The capture-side risk is twofold: **(i)** if HelixPlay's host agent injects into the game process (game-process-capture / ETW-overlay-injection style), the anti-cheat will detect the injection and ban the user — this is the explicit reason Sunshine uses DXGI Desktop Duplication (the OS-mediated path) rather than process-injection; **(ii)** if the capture process scans game memory (which Sunshine does NOT do, but some legacy capture libraries do), the anti-cheat treats the scan as a cheat behaviour. HelixPlay's C28 §9 binds the anti-cheat-aware capture posture as: **(a)** never inject into game processes — DXGI / WGC / ScreenCaptureKit / portal-PipeWire are all OS-mediated paths that anti-cheat-systems explicitly tolerate; **(b)** never read game-process memory — capture frames are GPU-resident textures, not CPU-resident process memory; **(c)** never enumerate game-process windows by title — use the OS-API's by-display capture that does not require window-handle enumeration; **(d)** publish a public-allowlist request to Vanguard / EAC / BattlEye when HelixPlay reaches the M3 milestone; **(e)** document the user-side warning that running HelixPlay on a host with Vanguard active may trigger BSOD-style conflicts when both kernel drivers contend for the same kernel-callback slots (the documented Vanguard ↔ EAC ↔ BattlEye co-existence problem on Battlefield 6).

## §H Frame-pacing alignment with VBLANK (NVIDIA Reflex / G-Sync / FreeSync VRR)

The C28 §10 frame-pacing-and-VBLANK-alignment binding is the most operator-visible aspect of the capture pipeline, because it determines the latency penalty between the game's actual rendering completion and HelixPlay's capture-acquire callback. The 2026 baseline is **(1)** NVIDIA Reflex on the host: Reflex measures the previous frame's render time and pauses the game thread for just the right amount of time to align CPU-GPU work with VBLANK, minimizing input → display latency; **(2)** VRR (G-Sync / FreeSync / VESA Adaptive-Sync): the display's refresh rate dynamically matches the GPU's output frame-by-frame, eliminating the fixed-VBLANK quantization penalty up to the VRR bound; **(3)** the `DXGI_PRESENT_ALLOW_TEARING` swapchain flag on Windows + `DwmFlush` synchronisation: the explicit tearing path that lets the game render through VBLANK without waiting, paired with `DwmFlush` for the windowed presentation case; **(4)** Sunshine's adaptive-capture-rate: Sunshine adjusts the capture rate to match the monitor's refresh rate at startup. The 2025 problem in the Sunshine GitHub issue tracker (Issue #1998) is that any kind of in-game frame-limiting (frame caps, V-Sync, RTSS limiter) tends to cause Sunshine micro-stuttering — the capture cadence falls out of phase with the game-engine cadence. HelixPlay's C28 §10 binds the frame-pacing posture as: **(a)** require Reflex-on at the game layer when the game supports it (HelixPlay's pre-flight check warns the operator if Reflex is off); **(b)** prefer VRR-on at the display layer (HelixPlay's pre-flight detects G-Sync / FreeSync / Adaptive-Sync support and configures the display); **(c)** match the capture cadence to the actual VBLANK rate at startup (Wayland: from `wl_output.mode`; Windows: from `IDXGIOutput::WaitForVBlank` + `DXGI_OUTPUT_DESC1.RefreshRate`; macOS: from `CGDisplayCopyDisplayMode` + `refreshRate`); **(d)** never apply HelixPlay-level frame-limiting on top of the game-level frame-limiting; **(e)** publish a per-frame timestamp through the SPSC ring so the encoder can adapt to phase drift over time.

## §Z Contradictions index (Z-1 .. Z-N)

The cross-reference between this addendum and the C28 chapter draws the following contradictions / open questions out for the chapter to resolve:

- **Z-1: NVFBC vs PipeWire DMA-BUF on Linux for NVIDIA hosts.** §D (NVFBC, lower-latency on supported drivers) vs §E (PipeWire DMA-BUF, licensing-clean and HDR-compatible). The §D evidence (NVFBC bypasses one compositor copy) competes with §E evidence (PipeWire is portal-mediated and HDR-supported). C28 §7 resolves the contradiction by tier-routing: NVFBC on Quadro / RTX PRO / Studio drivers (lower-latency, no HDR), PipeWire DMA-BUF on consumer GeForce drivers (licensing-clean, HDR-supported), with the per-host capability detector picking automatically.

- **Z-2: WGC vs DXGI Desktop Duplication on Windows 11 24H2.** §B records the 24H2 MPO regression that breaks DXGI on systems without MPO support, while WGC has its own latency penalty when the yellow capture border is required (Windows 11 21H1 / 22H2). C28 §5 resolves the contradiction by tier-routing: WGC on Windows 11 21H2+ with MPO-capable drivers and code-signed-publisher border opt-out; DXGI on Windows 10 / Windows 11 23H2 and earlier; both backends instantiable for runtime hot-switch on `DXGI_ERROR_ACCESS_LOST`.

- **Z-3: Capture cadence ↔ encoder cadence phase drift.** §H (Sunshine Issue #1998) documents the in-game frame-limiter ↔ capture-cadence phase-drift problem. The contradiction is between the Sunshine-recommended posture ("don't apply frame-limiting") and the operator's reality ("games and drivers apply frame-limiting independently"). C28 §10 resolves the contradiction by per-frame-timestamp publishing through the SPSC ring + encoder-side adaptive resampling on phase drift.

- **Z-4: ext-image-copy-capture-v1 vs xdg-portal screencast on Linux.** §A records two competing primary paths: `ext-image-copy-capture-v1` (lower-latency, no portal-dialog, headless-friendly) vs xdg-portal screencast (permission-prompted, sandbox-friendly, universally supported). C28 §3 resolves the contradiction by tier-routing: portal screencast in unprivileged / sandboxed deployment; `ext-image-copy-capture-v1` in privileged headless deployment; `wlr-screencopy` only as legacy fallback.

- **Z-5: SPSC ring depth (3 vs 8 vs other).** §C ScreenCaptureKit defaults to queueDepth=3 (max 8); §I PulseGeek recommends 3-frame depth for low-latency streaming. The contradiction is whether HelixPlay's SPSC ring depth should be 3 (matching ScreenCaptureKit / minimum-latency) or higher (matching encoder backpressure tolerance). C28 §3 resolves at depth=3 by default with a per-deployment override up to depth=8 for high-FPS / multi-stream scenarios.

- **Z-6: NVFBC RGB/BGR inversion regression on RTX 5090.** §F (Sunshine Issue #4504) records a 2025-Q3 regression on Blackwell that inverts the colour channel order in the NVFBC → NVENC pipeline. The contradiction is whether HelixPlay should ship NVFBC support on Blackwell at all until the regression is fixed upstream. C28 §7 resolves by adding a per-GPU regression-test gate to the capability detector: if the host is Blackwell and NVFBC is detected, run a colour-channel-validation capture before exposing NVFBC as a backend.

- **Z-7: Anti-cheat allowlist vs operator privacy.** §G records the per-anti-cheat-system allowlist mechanism (Vanguard / EAC / BattlEye). The contradiction is whether HelixPlay should request allowlist inclusion (lower BSOD risk, but discloses operator's HelixPlay usage to anti-cheat vendors) or not (higher BSOD risk, but preserves operator privacy). C28 §9 resolves by making allowlist-request opt-in with explicit operator consent at install time.

- **Z-8: VRR + capture-cadence interaction.** §H records the VRR-on-display ↔ capture-cadence interaction: when the display is in VRR mode, the capture cadence has no fixed target and must follow the GPU's actual frame-completion rate. The contradiction is whether HelixPlay should treat VRR as "capture every completed frame" or "capture at the display's reported max rate". C28 §10 resolves by capturing every completed frame and letting the encoder cadence (matched to the client's reported display refresh) be the throttle.

- **Z-9: Capture-process isolation cost.** §F (Sunshine++) argues for capture-process isolation; the cost is the per-frame IPC hop (SPSC ring + memory-fence / cache-line eviction). The contradiction is whether the isolation-cost (~100 ns per frame) is worth the resilience benefit (capture-process restart without parent-agent restart). C28 §2 resolves at "yes, the isolation cost is far below the VBLANK period and well worth the resilience benefit"; the ring-depth=3 default keeps the IPC cost under 300 ns per frame chain.

- **Z-10: Display latency floor on cloud streaming.** Insight #6 codifies the irreducible VBLANK floor on the host side. The contradiction is whether the floor is "irreducible at the host" (correct) or "irreducible end-to-end" (incorrect — the client-side has its own VBLANK floor). C28 §11 resolves by treating the floor as additive: host-VBLANK + transport + client-jitter + client-VBLANK = E2E floor; the 7-frame / 117 ms `ull` budget already accounts for both VBLANK floors and the rest.
