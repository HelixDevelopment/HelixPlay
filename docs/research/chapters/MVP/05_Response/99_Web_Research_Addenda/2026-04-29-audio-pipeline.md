## §A — Opus MultiStream over WebRTC: capabilities, signalling, and channel-mapping families

The transport layer for HelixPlay's WebRTC path is Opus. For
multi-channel game audio, the relevant primitive is *Opus
MultiStream* (RFC 6716 frame format + RFC 7845 Ogg channel-mapping
families + the in-flight `draft-shin-avtcore-rtp-multi-opus-01`
RTP/SDP signalling).

**Cluster facts (cited inline):**

- **Opus supports up to 255 channels** via *multistream* with explicit
  channel mapping. Modern surround layouts (5.1, 7.1) sit comfortably
  inside Channel Mapping Family 1 (1–8 channels, Vorbis order)
  ([RFC 7845 — Ogg Encapsulation for Opus][a-rfc7845],
  [Opus MultiStream API docs][a-opusms-api]).
- **Channel Mapping Family 1, Vorbis order:** 1 = mono; 2 = L,R; 3 =
  L,C,R (linear surround); 4 = FL,FR,RL,RR (quad); 5 = FL,FC,FR,RL,RR
  (5.0); 6 = 5.1 (FL,FC,FR,RL,RR,LFE); 7 = 6.1; 8 = 7.1 with side and
  rear pairs. **This Vorbis order is NOT Microsoft's
  WAVEFORMATEXTENSIBLE order — see §E for the channel-order mismatch
  hazard** ([RFC 7845 §5.1.1.2][a-rfc7845]).
- **Frame size sweep:** Opus supports 2.5 / 5 / 10 / 20 / 40 / 60 ms
  frames. Default 20 ms; ultra-low latency mode uses 2.5 ms frames in
  CELT-only "restricted low-delay" mode (~5 ms total algorithmic
  delay = 2.5 ms frame + 2.5 ms look-ahead). For HelixPlay, the
  game-audio path will pin Opus at 2.5 ms or 5 ms frames in CELT-only
  mode; voice-chat path can default to 20 ms SILK/Hybrid for VoIP
  intelligibility ([Opus Recommended Settings — Xiph][a-xiph],
  [Opus AES presentation: low-delay music coding][a-aes],
  [Opus Wikipedia summary][a-opus-wiki]).
- **WebRTC default audio codec is Opus** with Opus 1.3+ adding
  ambisonic / 3D surround support. Browser-level multi-channel
  reception works via the **non-standard `multiopus` SDP encoding
  name** introduced by libwebrtc, with `fmtp` parameters
  `num_streams`, `coupled_streams`, and `channel_mapping`
  ([draft-shin-avtcore-rtp-multi-opus-01][a-multiopus],
  [Janus WebRTC multi-Opus demo][a-janus],
  [MDN: Codecs used by WebRTC][a-mdn-webrtc]).
- **`multiopus` SDP example for 5.1** (Janus / libwebrtc-style):
  ```
  m=audio 9 UDP/TLS/RTP/SAVPF 96
  a=rtpmap:96 multiopus/48000/6
  a=fmtp:96 channel_mapping=0,4,1,2,3,5; num_streams=4; coupled_streams=2
  ```
  HelixPlay must emit exactly this `fmtp` line for libwebrtc-based
  endpoints; the in-flight IETF draft will eventually standardise
  this signalling so HelixPlay should track its progression as
  **OQ-V00-04** ([Janus multi-Opus][a-janus],
  [draft-shin-avtcore-rtp-multi-opus-01][a-multiopus]).
- **Opus MultiStream caps WebRTC at 8 channels** for practical
  HelixPlay use (7.1) — the 255-channel theoretical ceiling is
  unused outside ambisonic VR. **True Atmos object-audio (12+ object
  channels) cannot ride WebRTC's standard Opus path — passthrough
  only.** This is the binding constraint flowing into Insight #2 and
  §10 of the chapter index ([Opus codec — Wowza explainer][a-wowza]).
- **Opus has no native bitstream-passthrough mode for AC-3 / E-AC-3
  / TrueHD / DTS:X.** HelixPlay's Atmos / TrueHD / DTS-MA path must
  bypass Opus entirely and ride a separate "bitstream tunnel" RTP
  payload type, similar to how IEC 61937 frames the bitstream over
  S/PDIF — see §B and §I for the design implication.

**Implication for C31:** the chapter must specify two parallel audio
RTP tracks per session — `audio/opus` (or `audio/multiopus`) for
PCM-domain mix-down up to 7.1, and `audio/bitstream-tunnel`
(custom payload type, IEC-61937-framed) for AC-3 / E-AC-3-JOC /
TrueHD / DTS:X / DTS-MA passthrough. Capability negotiation (§I)
selects which track is active; both never run simultaneously for the
same session.

## §B — Atmos object-audio over Dolby Digital Plus + JOC / E-AC-3 (passthrough only)

Insight #2 makes Atmos a **passthrough-only** problem for the MVP.
Dolby has two physical-layer carriers for Atmos: lossy E-AC-3 with
Joint Object Coding (JOC) for streaming/HDMI, and lossless Dolby
TrueHD with Atmos extension for Blu-ray / eARC.

**Cluster facts:**

- **E-AC-3 (Dolby Digital Plus) carries Atmos via JOC.** The
  underlying bitstream is E-AC-3, channel-layout 5.1, and the JOC
  metadata side-channel reconstructs object audio (up to 15
  full-range objects + LFE) at the decoder. **Bitrate is increased
  vs. plain E-AC-3** — minimum 384 kbps, with 448 kbps and above
  commonly used. E-AC-3 itself supports up to 15 full-bandwidth
  channels at a max bitrate of 6.144 Mbit/s
  ([Dolby — What is Dolby Digital Plus JOC?][b-dolby-joc],
  [Wikipedia — Dolby Digital Plus][b-ddp-wiki]).
- **Dolby Atmos bitstreams are backwards-compatible:** an Atmos-DD+
  stream decodes as plain 5.1 on a non-Atmos decoder. This means a
  HelixPlay client that *thinks* it is Atmos-capable (via
  capability negotiation per §I) but is not (driver bug, EDID lie)
  will silently degrade to 5.1 — **the binary-threshold property of
  Insight #2 is partially softened by JOC's design** but the
  capability claim itself is what fails first
  ([Wikipedia — Dolby Digital Plus, Atmos extension][b-ddp-wiki]).
- **HDMI passthrough surfaces** for Atmos: bitstreams are carried as
  E-AC-3 (Dolby Digital Plus) over HDMI's audio sample packet stream
  (essentially IEC-61937-framed). The TV/AVR receives the
  unmodified E-AC-3 stream and decodes it. Apple's documented
  "HDMI Passthrough" lists EAC-3-JOC explicitly
  ([Apple Support — About HDMI Passthrough][b-apple-passthrough],
  [Dolby Hybrik — Dolby Audio overview][b-hybrik]).
- **Dolby Atmos vs. DTS:X comparison:** both are object-audio.
  Atmos is dominant on streaming (Netflix, Disney+ all use DD+JOC);
  DTS:X is mostly Blu-ray. Both ride eARC (lossless) for TrueHD-Atmos
  and DTS-MA-DTS:X
  ([What Hi-Fi? — DTS:X vs Atmos][b-dtsx],
  [Crutchfield — Learn DTS:X vs Atmos][b-crutchfield]).
- **Failure modes seen in the wild:** the WebOS-on-LG-TV passthrough
  bug (xbmc/kodi issue #23288) silently converts E-AC-3 to PCM,
  causing Atmos to vanish to stereo. Firecore's community thread
  documents the same class of bug across Apple TV firmware updates.
  HelixPlay must treat the passthrough chain as a **black-box that
  can lie** — it is not enough to detect Atmos capability at boot,
  the chain must be re-validated per-session
  ([xbmc/kodi #23288 — webos EAC-3 passthrough broken][b-kodi-bug],
  [Firecore — E-AC-3-JOC Atmos passthrough still does not work][b-firecore]).
- **E-AC-3-JOC encoding tooling for the MVP** is *not* a HelixPlay
  responsibility — the host emits whatever the game/OS produces.
  HelixPlay only needs to *carry* and *deliver* an unmodified
  E-AC-3 bitstream from host capture to client AVR
  ([Dolby Pro Support — exporting E-AC-3-JOC][b-dolby-export]).

**Implication for C31:** Atmos is a *capability claim* the chain
must defend at every link. C31 must spec a per-session
"passthrough probe" sequence: client requests a known E-AC-3-JOC
test pattern, the AVR is expected to light up its Atmos indicator,
client telemetry confirms; on failure → fall back to 7.1 PCM via
Opus MultiStream. **No silent fallback** — the user is told why.

## §C — eARC + HDMI 2.1 audio specifications

HDMI eARC (HDMI 2.1, 2017) is the *only* consumer interface that
can carry uncompressed multi-channel PCM and lossless Atmos /
DTS:X. This is the canonical link for HelixPlay's "TV → AVR" path.

**Cluster facts:**

- **eARC bandwidth jump:** ~1–3 Mb/s for legacy ARC → **37 Mb/s for
  eARC**. This is what unlocks uncompressed multi-channel and
  lossless object-audio
  ([What Hi-Fi? — HDMI ARC and eARC][c-whathifi],
  [TechHive — HDMI ARC and eARC explained][c-techhive]).
- **Capacity ceiling:** eARC delivers up to **32 channels of audio,
  including 8-channel 24-bit/192 kHz uncompressed PCM** at up to
  ~38 Mbps. 8 channels of 24-bit/192 kHz PCM = 36.864 Mbps (8 × 24
  × 192 000) — i.e., eARC is sized exactly for that worst case
  ([What Hi-Fi? — HDMI ARC and eARC][c-whathifi],
  [Ultimea — HDMI eARC and ARC][c-ultimea]).
- **Lossless object-audio:** eARC supports Dolby TrueHD
  (with Atmos extension) and DTS-HD Master Audio
  (with DTS:X extension). Plain ARC cannot — it is bandwidth-limited
  to lossy DD/DD+/DTS
  ([WyreStorm — HDMI ARC vs eARC][c-wyrestorm],
  [Crutchfield — what you need to know about HDMI ARC and eARC][c-crutch],
  [Home Theater Academy — Do You Need eARC for Atmos?][c-hta]).
- **Streaming-Atmos can ride plain ARC** because Netflix /
  Disney+ / Prime Video deliver Atmos as DD+JOC (lossy, ~768 kbps),
  which fits inside ARC's bandwidth. Lossless TrueHD-Atmos
  (~24 Mbps peak) requires eARC
  ([What Hi-Fi?][c-whathifi]).
- **HDMI cable requirements:** eARC negotiates over the HEAC
  channel pair; **High-Speed HDMI cable with Ethernet** is the
  minimum spec, **Ultra High-Speed HDMI** required for full HDMI 2.1
  feature parity (4K120, 8K60, eARC). HelixPlay's UX must surface
  cable-quality warnings — see C19 (TV UX) for the integration
  point ([FlatpanelsHD — HDMI ARC and eARC explained][c-flatpanels]).

[c-ultimea]: https://www.ultimea.com/blogs/news/hdmi-earc-and-hdmi-arc
[c-wyrestorm]: https://www.wyrestorm.com/blog/hdmi-arc-vs-earc/

Capability claim is then logged and re-validated per-session.

## §D — SPDIF / TOSLINK legacy: AC-3 + DTS bitstream only, 5.1 ceiling

S/PDIF (coaxial / TOSLINK optical) is the legacy fallback link.
**Hard ceiling: compressed AC-3 (DD 5.1) or DTS (DTS 5.1) — no
Atmos, no TrueHD, no DTS-MA, no 7.1 PCM.**

**Cluster facts:**

- **SPDIF / TOSLINK can carry compressed 5.1 Dolby Digital (AC-3)
  or DTS, framed in IEC 61937.** 5.1 PCM is *not* possible — only 2
  channels of uncompressed PCM fit in the ~6.144 Mbps frame
  ([Wikipedia — S/PDIF][d-wiki-spdif],
  [Wikipedia — TOSLINK][d-wiki-toslink],
  [HiFiMediY — Send/receive 5.1 DTS/AC3 via Optical S/PDIF][d-hifimediy]).
- **Bandwidth ceiling:** ~6.144 Mbps total. PCM stereo at 24/96
  fits comfortably; 24/192 stereo *can* work over coaxial but
  optical TOSLINK is spec'd to 24/96 — 24/192 over TOSLINK is
  out-of-spec and fragile
  ([AYRN — TOSLINK does support 24/192][d-ayrn],
  [PS Audio forum — Bandwidth limit of TOSLINK][d-psaudio],
  [Neutrino Audio — SPDIF coax vs TOSLINK vs AES/EBU][d-neutrino]).
- **No lossless surround at all:** "TOSLINK optical fiber connector
  does not possess the bandwidth capacity to carry the uncompressed
  audio signals of Dolby TrueHD and DTS-HD Master Audio"
  ([Wikipedia — TOSLINK][d-wiki-toslink]). 7.1 PCM, TrueHD, DTS-MA,
  Atmos, DTS:X are all impossible. This is the hard floor of the
  fallback ladder ([HiFi Walker — SPDIF Port Explained 2026][d-hifiwalker]).
- **Common myth correction:** users who think "SPDIF can't carry
  5.1" are usually trying to send 5.1 PCM — that fails. Bitstreamed
  AC-3 5.1 / DTS 5.1 work fine, the AVR decodes them. HelixPlay's
  fallback ladder must therefore distinguish "5.1 PCM" (impossible
  over SPDIF) from "5.1 AC-3" (possible) — the chain validation in
  §I must check the *encoded* format, not just the channel count
  ([AVS Forum — Optical SPDIF can't carry 5.1?][d-avsforum]).

and nothing else. Any session that negotiates Atmos or 7.1 over a
SPDIF-only client **must reject the upgrade** at session bootstrap.

## §E — Channel-order mismatch: Windows WAVEFORMATEXTENSIBLE vs. Dolby/DTS standard

This is the silent-corruption hazard that Insight #2 directly cites
("Windows 7.1 channel order differs from Dolby/DTS standard"). If
HelixPlay's capture does not fix it at the host, the client AVR
will play surround channels in the wrong locations — and the user
may not notice for hours.

**Cluster facts:**

- **Windows 7.1 channel order (WAVEFORMATEXTENSIBLE, mask `0x63F`):**
  `FL, FR, FC, LFE, BL, BR, SL, SR` — i.e., back-left/back-right
  *before* side-left/side-right
  ([Microsoft Learn — Channel Mask][e-msft-mask],
  [Microsoft Learn — WAVEFORMATEXTENSIBLE][e-msft-wfx]).
- **Industry standard (Dolby / DTS / SMPTE / Vorbis / ITU)
  7.1 order:** `FL, FR, FC, LFE, SL, SR, BL, BR` — sides *before*
  backs. Microsoft's choice was historically driven by 5.1 backward
  compatibility — when adding two channels for 7.1, Microsoft chose
  to *reverse* the surround pair rather than append the new
  channels at the end ([Mesh2HRTF wiki — Confusion of 7-1 channel
  order in Windows][e-mesh2hrtf],
  [MediaArea — Audio channel layout mapping][e-mediaarea]).
- **Vorbis order is the standard followed by Opus Channel Mapping
  Family 1 (RFC 7845) and by Linux PipeWire/PulseAudio.**
  HelixPlay's Opus encoder, if fed raw WASAPI buffers without
  re-ordering, will silently encode side and back channels in the
  wrong slots. The decoded output at a Linux/Android client AVR
  will then play, e.g., gunfire from "behind" actually firing from
  the side ([Steinberg Cubase docs — Surround channel
  configurations][e-steinberg]).
- **PipeWire / PulseAudio canonical surround names:**
  `front-left, front-right, rear-left, rear-right, front-center,
  lfe, side-left, side-right` — but the *order* in a 7.1 buffer
  depends on the channel-map; PipeWire's 7.1 default
  (`analog-surround-71`) uses `FL, FR, RL, RR, FC, LFE, SL, SR` —
  yet *another* permutation, which is itself non-Vorbis
  ([PipeWire — pipewire-pulse-modules man page][e-pipewire-mods],
  [PulseAudio modules docs][e-pulse-mods]).
- **Net effect:** there are at least **three** distinct 7.1 channel
  orderings (Microsoft WFX, Vorbis/Opus/Dolby, PulseAudio
  analog-surround-71). HelixPlay must define **one** internal
  canonical order (recommended: Vorbis / Opus Family-1 /
  Dolby) and explicit re-mapping shims at *every* boundary
  ([Microsoft Learn — Multichannel and High-Resolution WAV][e-msft-wav],
  [Steinberg Cubase docs][e-steinberg]).
- **Validation pattern (from research):** a known-good test stream
  encodes a sine sweep into one channel at a time; the user
  visually confirms speaker activity matches the labeled position
  on a small "channel test wizard" UI. This is mandatory at
  HelixPlay onboarding when a host or client first negotiates 5.1+
  ([Microsoft Learn WAV channel docs][e-msft-wav]).

## §F — PipeWire (Linux) audio capture, monitor sources, low-latency tuning

PipeWire is the canonical Linux audio stack for the host agent.
It supersedes the older PulseAudio capture surface while remaining
PulseAudio-API-compatible.

**Cluster facts:**

- **Monitor sources are auto-created** for every audio sink — e.g.,
  `alsa_output.pci-0000_04_00.6.analog-stereo.monitor` mirrors the
  *output* of that sink, which is exactly the loopback HelixPlay
  needs. No virtual driver install required
  ([PipeWire ArchWiki][f-arch],
  [PipeWire pw-loopback module docs][f-pwloop]).
- **`pw-loopback`** creates virtual loopback nodes between any two
  endpoints with explicit capture/playback property control. Useful
  for split-mixing the game audio from voice chat (cross-link to
  C06 voice-chat) ([pw-loopback man page][f-pwloop-man],
  [Arch BBS — pw-loopback setup][f-arch-bbs]).
- **Low-latency configuration:** `quantum=64` or `128` samples at
  48 kHz → ~1.3 ms or ~2.7 ms quantum latency. Real-time scheduling
  (rtkit + `audio` group) is mandatory; without it the kernel
  scheduler can preempt the audio thread and cause glitches even at
  low CPU usage. Professional recording targets stable <10 ms total
  latency ([Botmonster — Fix PipeWire low-latency][f-botmonster],
  [OneUptime — Configure PipeWire for low-latency on Ubuntu][f-oneuptime]).
- **PipeWire over PulseAudio shim:** the `pipewire-pulse` daemon
  exposes the legacy PulseAudio API surface so tools that capture
  via libpulse (e.g., `pactl`, `parecord`, OBS) keep working
  unchanged. HelixPlay's host agent should prefer **native PipeWire
  graph API** (lower overhead, finer-grained latency control) but
  fall back to libpulse for older distros
  ([PipeWire pulse modules][e-pulse-mods]).
- **Surround channel mapping:** `iec958-ac3-surround-51` for AC-3
  bitstream over SPDIF, `analog-surround-71` for 7.1 PCM. Note the
  channel-order issue from §E — PipeWire's analog-surround-71 uses
  `FL,FR,RL,RR,FC,LFE,SL,SR` which is **not** the Vorbis/Opus order
  ([PipeWire pulse modules][f-pulse-mods]).
- **HDMI passthrough on Linux is fragile:** historically requires
  ALSA-direct access bypassing PipeWire's resampling for IEC-61937
  bitstream framing. Recent PipeWire versions (1.0+) added native
  passthrough sink support with `node.passthrough = true`
  ([NixOS Discourse — A52 AC3 surround through PipeWire-ALSA][f-nixos],
  [Arch BBS — PipeWire and Pulse][f-arch-pulse]).

## §G — WASAPI loopback (Windows): multi-channel surround capture

WASAPI is the only sane Windows audio API for low-latency game
capture. Loopback mode is what makes it a capture surface for game
audio at all.

**Cluster facts:**

- **WASAPI loopback** captures the audio stream *being played by* a
  rendering endpoint device. It runs only in shared mode
  (`AUDCLNT_SHAREMODE_SHARED`) — exclusive mode cannot loopback
  ([Microsoft Learn — Loopback Recording][g-msft-loop],
  [NAudio WasapiLoopbackCapture docs][g-naudio]).
- **Hardware vs software loopback:** if the audio adapter exposes a
  hardware loopback pin, WASAPI uses it (zero CPU cost). Otherwise,
  WASAPI copies the engine output stream into the loopback buffer.
  HelixPlay can't choose which path is used — it depends on the
  device driver ([Microsoft Learn loopback ref][g-msft-loop]).
- **Application loopback (Windows 10 2004+)** lets a process capture
  *only* a specified subset of processes' audio (or all *except*
  some). This is critical for separating game audio from
  voice-chat audio so they can be encoded onto separate Opus
  streams (game music + voice) — cross-link to C06 (voice chat)
  ([Microsoft Learn — Application loopback audio capture sample][g-msft-app-loop]).
- **Multi-channel surround capture:** 7.1 game output is captured as
  an 8-channel buffer in WAVEFORMATEXTENSIBLE order (mask `0x63F`,
  the Microsoft order from §E). HelixPlay must apply the channel-
  order shim before Opus encoding ([Multimediasoft WASAPI
  tutorial][g-multimediasoft]).
- **Exclusive-mode is required for Atmos bitstream passthrough.**
  Atmos / TrueHD / DTS-HD Master Audio cannot ride WASAPI
  shared-mode (mixer downmixes to PCM). HelixPlay's Atmos path must
  open the endpoint in **exclusive mode** for the duration of the
  stream — meaning *no other Windows audio can be captured* during
  that session. This is a hard architectural fork in the host
  agent ([ResetEra — Exclusive mode in Windows for Atmos / 5.1 /
  7.1][g-resetera],
  [Kodi forum — Atmos on Windows 10 and Kodi guide][g-kodi-atmos]).
- **Spatial Sound API** is Microsoft's path to Atmos for *game
  engines* (the engine emits 7.1.4 LPCM beds + object metadata; the
  Spatial Sound runtime encodes to Atmos). HelixPlay does not
  intercept this — the host captures the *post-Spatial-Sound*
  output. If the user has "Dolby Atmos for Home Theater" enabled,
  HelixPlay sees an E-AC-3-JOC bitstream at the WASAPI endpoint and
  must capture it via exclusive-mode passthrough
  ([Microsoft Learn — Spatial Sound for app developers][g-msft-spatial],
  [PCNMobile — Activate Atmos in Windows 11][g-pcnmobile]).
- **Known WASAPI loopback bugs (Windows 11 ARM):** on Windows 11
  ARM, `IAudioCaptureClient::GetNextPacketSize` reportedly always
  returns 0 — silent capture failure. HelixPlay's CI must include
  Windows ARM hardware in its capture-test matrix
  ([Microsoft Q&A — CoreAudio WASAPI loopback Win11 ARM][g-msft-arm-bug]).

## §H — CoreAudio (macOS): process taps + aggregate devices

macOS 14.2+ introduced the **Core Audio Tap API** which finally
enables system-audio capture without third-party kernel extensions
(legacy "Soundflower" / "BlackHole" model). This is the canonical
HelixPlay capture surface on macOS.

**Cluster facts:**

- **Core Audio taps capture outgoing audio from a process or set of
  processes**, replacing the older "loopback device that mirrors
  output as a 6-channel mic" pattern. Introduced macOS 14.2;
  permission gating tightened in 14.4 (NSAudioCaptureUsageDescription
  Info.plist key required) ([Apple Developer — Capturing system audio
  with Core Audio taps][h-apple],
  [insidegui/AudioCap sample code][h-audiocap]).
- **`CATapDescription`** is the descriptor; flow is:
  1. Create `CATapDescription` for the target process(es).
  2. Call `AudioHardwareCreateProcessTap` — get an `AudioObjectID`.
  3. Build an aggregate device dictionary that includes the tap UUID
     in `kAudioAggregateDeviceTapListKey`.
  4. Call `AudioHardwareCreateAggregateDevice`. The aggregate device
     exposes the tapped audio as an input stream
  ([Maven blog — CoreAudio Taps for Dummies][h-maven],
  [Sudara gist — Core Audio Tap API example][h-gist]).
- **Multi-channel capture:** the system can deliver mono or stereo
  mix-down by default; for explicit channel layouts (5.1, 7.1) the
  caller must construct a "real (fake) device" prescribing the
  desired format ([miniaudio issue #875 — Loopback support on macOS
  using new CoreAudio tap API][h-miniaudio]).
- **Permission UX:** taps require TCC privacy authorization; UI
  shows a *purple* dot rather than the orange "microphone" dot.
  HelixPlay's onboarding must request this at first run; deny =
  audio degrades to silent (no fallback to mic) — UX must surface
  the failure clearly ([Strongly Typed — AudioTee blog][h-strongly]).
- **Aggregate devices** alone (without taps) can also combine
  multiple audio interfaces; HelixPlay does not need this for
  capture but should be aware that user-created aggregate devices
  can interact with tap registration in surprising ways
  ([Apple Support — Create an Aggregate Device][h-apple-agg],
  [Rogue Amoeba — Loopback drift correction][h-rogue]).
- **Drift correction is mandatory** for aggregate devices spanning
  multiple physical clocks. HelixPlay's tap-on-aggregate-device
  config rides the system clock, so this is mostly transparent —
  but if a user has a USB audio interface in the aggregate, the
  drift-correction checkbox in Audio MIDI Setup matters
  ([macProVideo — Aggregate Devices in Audio MIDI Setup][h-mac-mpv]).
- **No Atmos passthrough API in CoreAudio for taps:** the tap
  delivers PCM mix-down. macOS Atmos passthrough (eARC / HDMI) is
  handled by the system audio framework's *output* path, not the
  tap *input* path. HelixPlay on macOS therefore **cannot**
  passthrough Atmos from a host Mac → client; macOS hosts are
  PCM-only (max 7.1 via Opus MultiStream). This is a constraint to
  flag in `OQ-V00-04`.

## §I — Audio capability negotiation chain (game → OS → capture → encode → transmit → decode → AVR)

This is the integration cluster that operationalises Insight #2.
The capability is **the conjunction of every link's claim**; failure
at any link forces fallback. C31 must define a session-bootstrap
capability-probe protocol covering all seven links.

**Cluster facts:**

### I.1 — Game / engine layer (link 1)
- **Wwise and FMOD power >90% of AAA games.** Wwise supports up to
  7.1 natively (added Oct 2013); FMOD supports up to 7.1 via Vector
  Based Amplitude Panning. Both respect the OS speaker layout (i.e.,
  whatever Windows / macOS / Linux reports as the output channel
  config, the engine renders to)
  ([Audiokinetic — Wwise][i-wwise],
  [FMOD low-level API overview][i-fmod],
  [Game Audio Co — Wwise vs FMOD][i-gaco],
  [Audiokinetic blog — Mastering a game with Wwise][i-wwise-mastering]).
- **Atmos requires a 7.1.4 LPCM bed routed via Microsoft Spatial
  Sound API or Sony's Tempest (PS5)** — Windows games emit Atmos
  metadata via Spatial Sound, which the OS encodes to E-AC-3-JOC at
  the system mixer. HelixPlay captures the *output* of that mixer,
  not the engine's pre-Spatial-Sound buffers
  ([Microsoft Learn — Spatial Sound][g-msft-spatial],
  [AVS Forum — Dolby Atmos for gaming thread][i-avsforum-atmos]).

### I.2 — OS audio stack (link 2)
- **Windows:** WAVEFORMATEXTENSIBLE order (§E hazard) +
  shared-vs-exclusive WASAPI choice (§G).
- **Linux:** PipeWire native graph + monitor sources (§F).
- **macOS:** CoreAudio tap on aggregate device (§H).

### I.3 — Capture (link 3)
- Per-OS shim — see §F/§G/§H. Output is normalised to
  HelixPlay's internal canonical channel order (Opus Family 1 /
  Vorbis order — §E).

### I.4 — Encode (link 4)
- **PCM path:** Opus MultiStream up to 8 channels (Family 1) for
  ≤7.1; CELT-only mode 2.5 ms frames for game audio, SILK/Hybrid 20
  ms for voice. Bitrate budget per channel pair: ~64–128 kbps for
  music-quality, ~32–64 kbps for voice
  ([Opus Recommended Settings — Xiph][a-xiph]).
- **Bitstream path:** E-AC-3-JOC / TrueHD / DTS:X passed through
  unmodified, IEC-61937-framed, in a custom RTP payload type. No
  re-encode (would destroy Atmos metadata).

### I.5 — Transmit (link 5)
- WebRTC PCM track via `audio/multiopus` SDP signalling (§A).
- WebRTC bitstream-tunnel via custom RTP payload (deferred to
  HelixPlay-custom UDP path on LAN — cross-link to C09 transport).

### I.6 — Decode (link 6)
- Client-side: Opus MS decoder (libopus) for PCM. For bitstream
  tunnel, the client *forwards unmodified* IEC-61937 frames to the
  AVR via the platform passthrough API (eARC for TV-clients, HDMI
  bitstream for PC-clients).

### I.7 — AVR / display capability (link 7)
- **EDID Short Audio Descriptors (SADs)** declare what the
  TV/AVR can decode. Each SAD is 3 bytes:
  * Byte 1: bits 6–3 = format code (1=LPCM, 2=AC-3, 6=AAC, 7=DTS,
    10=DD+, 11=DTS-HD, 12=MLP/TrueHD); bits 2–0 = channels minus 1.
  * Byte 2: sampling-rate bitfield (32/44.1/48/88.2/96/176.4/192).
  * Byte 3: bit-depth (LPCM) or max bitrate (others)
  ([Wikipedia — EDID][i-edid-wiki],
  [Extron — Understanding EDID][i-extron],
  [Doctor HDMI — EDID dictionary][i-drhdmi]).
- **HelixPlay's TV client must read its own EDID** (where the
  platform exposes it) **and forward an authoritative
  capability-summary** to the host at session bootstrap. On
  platforms with no EDID access (web browsers), HelixPlay falls
  back to a probe-and-validate pattern (try-fail-downgrade, see §B).
- **Reference EDID parser** — open-source EDID generator for SADs:
  `hidenorly/HdmiEdidShortAudioDescriptorGenerator` is a useful
  reference for the binary layout
  ([GitHub — HdmiEdidShortAudioDescriptorGenerator][i-edidgen],
  [Gesight — Understanding HDMI and E-EDID][i-gesight],
  [UnifiedCommunications — Unpacking EDID][i-uc],
  [archive.org — CTA-861-G full text][i-cta861]).
- **`CTA-861-G` is the controlling spec** for HDMI EDID extension
  blocks including SADs. HelixPlay's EDID parser must match the
  SAD byte layout exactly — silent mis-parse → silent capability
  lie → silent stereo fallback ([CTA-861-G][i-cta861]).

### I.8 — Voice chat integration (cross-link to C06)
- HelixPlay must support a separate voice-chat audio track per
  session (game audio is *not* mixed with voice at the host). The
  client mixes game-audio and voice locally for output, applying
  user-configurable ducking
  ([Discord — Game Overlay 101][i-discord-overlay],
  [Discord support — Auto-ducking off][i-dataconomy]).
- **Discord-style auto-ducking** lowers other-app audio when a
  speaker is detected; the same algorithm applies to HelixPlay's
  client-side mix. Voicemeeter is the reference on Windows;
  PipeWire's pw-loopback can implement the same on Linux
  ([Joe Dynamite — Voicemeeter Discord setup][i-joedyn],
  [Linux Mint — Audio ducking for Discord][i-linuxmint]).
- **Why this matters for capability negotiation:** if the host is
  passthrough-only (Atmos bitstream tunnel), there is **no PCM
  domain** in which to mix the HelixPlay UI sounds (notifications,
  voice-chat-mixed-in) with the game audio. C31 must spec that
  in passthrough mode, HelixPlay UI/voice audio rides a **separate
  Opus PCM track** mixed at the *client* — the AVR receives Atmos
  via passthrough, and the TV/client speakers handle voice/UI
  inline. This is the architectural consequence of Insight #2.

### I.9 — Downmix / upmix matrices for graceful degradation
- **LtRt (Left Total / Right Total)** matrix encoding allows a 5.1
  → stereo downmix that decodes back to 5.1 via Dolby Pro Logic
  decoders. **LoRo (Left Only / Right Only)** is a plain stereo
  downmix with no surround re-encoding
  ([Dolby — Downmix settings article][i-dolby-downmix],
  [TVTechnology — What is upmixing?][i-tvt],
  [Production-Expert — How to create 2.0 stereo from surround][i-prod-expert],
  [HitPaw — Downmix 5.1 to stereo guide 2026][i-hitpaw]).
- **HelixPlay's fallback ladder** uses LoRo when all the user has is
  stereo (no Pro Logic decoder expected) and the input was 5.1.
  The Opus encoder doesn't downmix — HelixPlay does the LoRo
  downmix in the host capture pipeline before encoding, only when
  capability negotiation has confirmed the client tops out at
  stereo PCM.
